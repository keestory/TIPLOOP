# 제품 감각 (Product Sense)

> PM, Designer, QA 에이전트가 공통으로 참조하는 제품 원칙

## 사용자 중심 원칙

### 1. 사용자가 누구인가?

| 페르소나 | 역할 | 핵심 니즈 | 기술 수준 |
|----------|------|----------|----------|
| 엔지니어 | 에이전트를 운영하는 사람 | 빠른 구현, 안정적 실행, 최소 개입 | 높음 |
| PM | 제품 방향 결정자 | 요구사항 명확화, 진행 추적, 품질 확인 | 중간 |
| 최종 사용자 | 에이전트가 만든 제품을 사용하는 사람 | 직관적 UI, 빠른 응답, 신뢰성 | 다양 |

### 2. 제품 의사결정 프레임워크

모든 기능 결정에 이 순서로 질문:

1. **사용자 가치**: 이것이 사용자의 어떤 문제를 해결하는가?
2. **빈도**: 이 기능을 얼마나 자주 사용하는가?
3. **대안**: 이것 없이 사용자는 어떻게 하고 있는가?
4. **비용**: 구현 및 유지 비용 대비 가치가 충분한가?
5. **리스크**: 잘못되면 어떤 피해가 발생하는가?

### 3. MVP 사고

- 완벽한 기능 1개 > 불완전한 기능 5개
- 수동 워크어라운드가 가능하면 자동화를 미뤄도 됨
- "사용자가 이것 없이 제품을 사용할 수 있는가?" → 있다면 MVP 이후

## 에이전트 시스템의 제품 가치

### 속도 메트릭
| 지표 | 목표 | 측정 방법 |
|------|------|----------|
| PR 처리량 / 엔지니어 / 일 | ≥ 3 | git log 카운트 |
| 기능 구현 리드타임 | < 4시간 | 이슈 생성 → PR 병합 |
| 버그 수정 리드타임 | < 2시간 | 리포트 → 배포 |
| 리뷰 루프 평균 반복 | ≤ 2회 | 리뷰 사이클 카운트 |

### 품질 메트릭
| 지표 | 목표 | 측정 방법 |
|------|------|----------|
| 에이전트 태스크 성공률 | ≥ 85% | 성공/전체 비율 |
| 아키텍처 린트 위반율 | ≤ 1% | 린터 결과 |
| 문서 최신화율 | ≥ 90% | doc-gardener 스캔 |
| 사용자 보고 버그 | 주당 ≤ 3건 | 이슈 트래커 |

### 비용 메트릭
| 지표 | 목표 | 측정 방법 |
|------|------|----------|
| 기능당 API 비용 | < $5 | claude 출력 cost_usd 합계 |
| 리뷰당 비용 | < $2 | 리뷰 루프 비용 |
| 가비지 컬렉션 비용 / 일 | < $1 | GC 실행 비용 |

## 제품 로드맵 관리

### 계획 아티팩트

| 문서 | 위치 | 역할 |
|------|------|------|
| 제품 사양 | `docs/product-specs/` | 기능별 상세 요구사항 |
| 실행 계획 | `docs/exec-plans/active/` | 구현 단계 및 진행 상태 |
| 기술 부채 | `docs/exec-plans/tech-debt-tracker.md` | 알려진 부채 추적 |
| 품질 등급 | `docs/QUALITY_SCORE.md` | 도메인별 현재 상태 |

### PM ↔ 엔지니어링 핸드오프

```
PM: 제품 사양 작성 (docs/product-specs/)
 ↓
Planner: 실행 계획 수립 (docs/exec-plans/active/)
 ↓
Coder: 구현
 ↓
QA: 수용 기준 검증
 ↓
Designer: UX 검증 (해당 시)
 ↓
Reviewer: 코드 리뷰
 ↓
PM: 최종 확인 → 배포 승인
```
