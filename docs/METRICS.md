# 지표 가이드

> analyst 에이전트가 참조하는 데이터 분석 원칙

## 지표 설계 원칙

### 기능마다 성공 지표를 먼저 정의한다
기능을 만들기 전에 "이것이 성공하면 어떤 숫자가 변하는가?"를 정의한다.
정의할 수 없으면 기능의 목적이 불명확한 것이다.

### 핵심 지표 + 가드레일
- **핵심 지표**: 이 기능이 개선하려는 것 (예: 전환율)
- **가드레일**: 핵심 지표를 올리면서 깨뜨리면 안 되는 것 (예: 페이지 로딩 시간, 이탈률)
- 핵심 지표가 올라도 가드레일이 무너지면 실패

### 허영 지표를 경계한다
- 페이지뷰, 가입 수 — 그 자체로는 의미 없음
- "이 숫자가 변하면 어떤 의사결정을 내릴 것인가?" → 답이 없으면 허영 지표

## 데이터 수집

### 이벤트 설계
기능을 구현할 때 analyst가 필요로 하는 이벤트를 함께 정의한다.

필수 속성:
- 이벤트명 (동사 + 명사: `click_purchase_button`)
- 사용자 ID (익명 처리된)
- 타임스탬프
- 컨텍스트 (어떤 화면, 어떤 실험군)

### 로깅 vs 이벤트
- 로깅: 디버깅/운영용 (ops가 본다)
- 이벤트: 분석용 (analyst가 본다)
- 같은 데이터를 두 곳에 넣지 말 것. 용도가 다르다

## 분석 프레임워크

### 퍼널 분석
사용자의 목표 달성 경로에서 어디서 이탈하는가?
→ 이탈이 가장 큰 단계를 개선하는 게 가장 효과적

### 코호트 분석
신규 사용자 vs 기존 사용자, 유료 vs 무료 등
동일한 기능이 사용자 그룹별로 다르게 작동할 수 있다

### A/B 테스트
확신이 없을 때 데이터로 결정하는 방법.
- 충분한 표본이 모일 때까지 기다린다
- 조기 종료하지 않는다 (p-hacking 방지)
- 하나의 실험에서 하나의 변수만 변경

## PM ↔ Analyst 협업

```
PM: "이 기능을 만들려고 합니다"
Analyst: "성공 지표는 뭔가요?"
PM: "전환율 5% 향상"
Analyst: "가드레일은 로딩 시간과 이탈률로 하겠습니다. 
         이벤트는 이것들이 필요합니다. 
         판단은 출시 7일 후에 하겠습니다."
```
